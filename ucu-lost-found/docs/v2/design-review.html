Stage 1 · Discovery

What we found

The existing codebase is a solid v1, not a blank slate

React 19 + Vite, Express 5, MySQL 8. It already has bcrypt hashing, server-side hashed session tokens, Helmet, login rate limiting, zod validation on both sides, private finder details, claims, admin review, confirmed returns, an audit table, 30 API tests and a Playwright walkthrough.

The database already enforces one approved claim per item with a generated-column unique index. We keep that design.

Plan: evolve v1 into v2 through migrations, keeping what works and not starting again.

Gaps against the v2 brief

  • Login uses email. v2 needs the registration number as the identifier, plus a controlled student registry.
  • No password recovery, account activation, admin roles or account deactivation.
  • No matching engine and no notification centre.
  • One photo per report, stored as a BLOB. v2 supports several images with access control.
  • The location list doesn't match the 16 campus locations you supplied, and locations can't be managed.
  • The design is navy and gold. v2 moves to the white, blue and pink system below.

UCU Alpha portal (reference)

  • Material-style UI in Roboto, on a full-bleed campus photograph with a dark overlay.
  • One centred card with the identity at the top and a two-step sign-in (identifier first, then the next step).
  • Its primary button is a saturated pink (#E91E63) with an 8px radius, on navy text.
  • A short utility nav runs along the top: Home, Profiles, Careers, Staff/Student email.

We borrow the calm hierarchy, the single focused card and the strong colour on navy text. We don't copy the layout, and the badge is an original design rather than the crest.

Repository hygiene issue

The repo has no .gitignore, and 8,790 files from client/node_modules are committed. That makes clones heavy, and a .env could get committed by accident.

First commit of v2: add a .gitignore and run git rm -r --cached on node_modules. No secrets are tracked at the moment (checked).

Reference screenshots. The two "Lost and Found Manager" screenshots are commercial staff tools: coloured tiles, a quick-entry grid of common item types, inquiry lists and match notifications as toasts. We take the quick-entry by item type idea and the idea of a matching queue as its own admin area. We leave out the bright four-colour tile style, which would clash with a restrained white, blue and pink system.

Product identity

UCU Findora

Chosen name

UCU Findora

Findora (fin-DOR-a) is built from find and reads like the name of a place: the place on campus where things turn up. The UCU prefix tells every student straight away that it's the university's own lost-property service, not a random app.

In the app header and on small screens it can shorten to "Findora". Taglines: "Lost it on campus? Let's get it back." · "Everything found, at UCU."

Using the UCU name and a badge

A name and logo that carry "UCU" read as an official university service. The badge below is an original shield. It doesn't copy the official crest (no Alpha and Omega, cross or dove), so it won't be mistaken for the university seal.

Before a public launch, get written approval from the university (for example its communications office or ICT directorate). Until then the footer reads "Student project, not yet an official UCU service".

Logo concept: the Findora badge

A shield, the shape students know from university crests and sports badges, with UCU across the top. Below the line sits a pink location pin holding a U-shaped arrow that turns back on itself: the item coming home. The shield is UCU blue, and the pin is the only pink, because pink means "something was found". A one-colour version covers stamps, printed receipts at the collection desk and the browser tab icon.

Behaviour

  • The registration number is normalised (trimmed, upper-cased) before lookup, and stored unique.
  • A wrong number and a wrong password give the same message: "Registration number or password is incorrect."
  • After 5 failures the account is locked for 15 minutes, and IP rate limiting applies on top. The lock message doesn't confirm the account exists.
  • "Keep me signed in" issues a 30-day session instead of 8 hours. It's a hashed server-side token like v1, so logging out or resetting the password kills it.

Accessibility

  • Real <label>s, autocomplete="username" / "current-password" and an error summary that links to each field.
  • The Show/Hide toggle is a button with aria-pressed.
  • On phones the navy panel collapses to a 64px brand strip and the form fills the screen.

Module 7

The matching engine

Rule-based, explainable and deterministic. No AI service. Every match stores its score breakdown, so a student sees why ("same category · same place · same day") and an admin can check whether the rules are well tuned.

1 · Hard filters (candidate selection in SQL)

  • Compare lost ↔ found only. Never lost↔lost or found↔found.
  • Both reports status = 'open'. Returned, closed or removed items never match.
  • Different reporters. A finder is never told they own what they reported.
  • Date window: found_date ≥ lost_date − 1 day and found_date − lost_date ≤ 30 days.
  • Same top-level category or a title-token overlap. This keeps the candidate set small (an indexed query, tens of rows).

2 · Weighted score (pure function, unit-tested)

score = 0.35·name + 0.25·category
      + 0.20·location + 0.15·date
      + 0.05·description

The weights live in settings so an admin can tune them. Each factor is between 0 and 1.

FactorHow it's measured
Name (35%)Normalise (lower-case, strip punctuation, singularise, synonym map: phone↔mobile↔smartphone, charger↔adapter, bottle↔flask, ID↔identity card), drop colour and brand words. Then 0.6 × token containment + 0.4 × trigram Dice. Containment uses the shorter title, so "Calculator" against "Casio calculator" still scores high.
Category (25%)Same category = 1. Same parent category (for example Electronics) = 0.5. Otherwise 0.
Location (20%)Same location = 1. Same zone (for example K Block and Computer Laboratories in the "Academic core") = 0.5. Either side "Other / not listed" = 0.3. Otherwise 0.
Date (15%)Δ = days between the dates. Δ ≤ 1 → 1, then 1 − (Δ − 1) / 13, reaching 0 at Δ = 14.
Description (5%)Jaccard overlap of public description keywords after removing stop-words. It never uses confidential details.

Strong / likely match

Stored as suggested. The lost report's owner gets an in-app notification (and email, if enabled) once per pair. The match also appears in the admin match queue.

0.50 – 0.69

Possible match

Stored and shown under "Potential matches" on the student dashboard, with no push notification. This keeps false alerts down.

< 0.50

Not a match

Not stored. Thresholds are settings and will be calibrated against about 200 fictional seed reports before launch.

When it runs and how duplicates are prevented

  • On create: a new found report is scored against open lost reports, and a new lost report against open found items. The lost-side owner immediately sees existing matches.
  • On update (title, category, location, date, description): the pairs for that report are re-scored with INSERT … ON DUPLICATE KEY UPDATE. A pair whose score drops below 0.50 is set to expired.
  • Notify once: a notification is sent only when notified_at IS NULL and the score crosses 0.70. It's written with dedupe_key = "match:{lost}:{found}" under a unique index, so retries and re-scores can't send it twice.
  • Return closes everything: confirming a return sets the item to returned, expires its matches, closes the linked lost report (if the claimant had one) and blocks new claims. All of it happens in one transaction.
  • The student can dismiss a match ("not mine"). It's hidden and never re-notified.
  • Matching runs in-process after the report transaction commits. A nightly sweep re-scores the date-window edges, so nothing is missed if a request fails halfway.
Security

Authentication, activation and password recovery

We have no verified connection to UCU's student systems, so v2 uses an administrator-managed student registry. Staff import a CSV of registration numbers, names and university emails from an authorised export, and only numbers in the registry can be activated. If UCU later approves an integration (for example SSO), it can replace the registry import without changing the rest of the system.

Student activation (replaces open sign-up)

  1. The student enters their registration number and full name.
  2. If the number is in the registry, enrolled and not yet activated, a 6-digit code goes to the university email on file. The screen always says "If those details match our records, we've sent a code to your university email", whether or not they matched.
  3. The student enters the code (10 minutes, 5 tries), then sets a password (at least 10 characters, checked against a common-password list).
  4. The account is created as active and signed in. The action is logged.

No university email on file: the student goes to the lost-property office with their ID card, and an officer issues a one-time activation link. That action is also logged.

Administrator accounts

  • There's no self-registration. A super admin creates an admin account and the new admin gets a one-time "set your password" link.
  • Separate endpoint /admin/auth/login, using a staff ID. Sessions last 4 hours, and admins re-enter their password for sensitive actions (creating admins, registry import).
  • Deactivating an account revokes all of its sessions immediately.
  • Phase 2 option: TOTP two-factor for admins.
  • The first super admin is created by a one-off CLI script (npm run admin:create), never by seed data in production.

Password storagebcrypt, cost 12 (v1 already does this). Passwords are never logged or emailed.
SessionsA random 256-bit token in an httpOnly, Secure, SameSite=Lax cookie. Only the SHA-256 hash is stored. They're revoked on logout, password reset and deactivation.
CSRFSameSite cookie plus an Origin header check on every state-changing request.
EnumerationLogin, activation and forgot-password responses are generic, with similar response times.

UploadsJPEG, PNG and WebP only. The file type is checked from its contents, not the name. 5 MB limit, at most 4 images. Images are re-encoded with sharp, which strips EXIF and GPS data. Files get random 32-byte keys, live outside the web root and are served through an access-checked route.

Before we build

Decisions we need from you

University approval for the name and badge

UCU Findora uses the university’s name and a badge-style mark. Who at UCU should approve this before launch, and should we show the footer disclaimer until then?

Registration number format and the registry source

What's the exact format (please share a real one with digits changed), and can the registrar provide a CSV with university emails? If there's no email, recovery goes through the office in person.

Email delivery

Activation and password reset need an approved sender (a university SMTP relay or a transactional email service). Development uses a local mail catcher, so this can wait until deployment.

Tailwind or plain CSS

We recommend Tailwind with the tokens above. Plain CSS keeps v1's approach but is harder to keep consistent across the admin screens.

Where found items are physically held

One central office (the "Dean of Students" in the mock-ups is an assumption), or the finder keeps the item until a claim is approved? This changes the found-item form and the collection instructions.

Hosting target

v1 includes a Render blueprint. For v2 we need managed MySQL plus object storage. Is the plan a university server or a cloud host?
